CodeWeave · handbook

Every screen, every button, and what GitHub lets you do

CodeWeave reads one GitHub repository at a time, answers questions from its real code, works out what a change would break, and can open a pull request for you. What it will let you do depends entirely on what GitHub says you can do to that repository — so this guide runs the whole tour twice: once for a repository you own, once for someone else's.

Vocabulary

Six GitHub words, then nothing else is confusing

Every button in CodeWeave maps onto one of these. If you know these six, you know what the app is doing.

Repository (repo)
A project's folder of code, its history, and who is allowed to touch it.
The thing you point CodeWeave at. One repo is analysed at a time.
Branch
A parallel copy of the code you can change without touching the main version. main is the default branch — the one everyone treats as real.
Every AI change gets its own new branch, e.g. codeweave/reject-negative-credits-0bziwh. CodeWeave never writes to main directly.
Commit
One saved step in the history: "these files changed, for this reason." Identified by a hash like 756b975.
All files in one accepted change are saved as a single commit, with a message you can edit first.
Pull request (PR)
A proposal: "please merge my branch into yours." It shows the diff and lets people comment before anything is merged.
The end of the change flow. CodeWeave opens it; a human merges it. It never merges anything.
Fork
Your own copy of someone else's repository, under your account. You can commit to your copy freely, then send a pull request back to theirs.
How you propose changes to a repo you don't own.
Webhook
GitHub phoning an app when something happens — a push, a new pull request.
Keeps the index fresh and reviews new pull requests without you asking.

Permissions

CodeWeave can only ever do what your GitHub account can do

There is no CodeWeave account and no password. You authorize the CodeWeave GitHub App, GitHub hands the server a short-lived token that belongs to you, and every read and write happens as you. So the badge at the top of a repository is not CodeWeave's opinion — it is GitHub's answer about your account.

Read & write

GitHub reports push access. Changes go straight into a new branch on this repository, then a pull request.

your own repos · repos you collaborate on

Read only

You can analyse, ask, and generate changes. To propose one, it goes through a fork under your account.

public repos owned by other people

No access

A private repository your account can't see is refused outright — no metadata, no file names.

someone else's private repo

The App installation matters too. Installing CodeWeave on an account is what lets it write there. Installations are per-account and not shared: an installation on alice gives no power over bob's repositories, even if the same person owns both accounts. This is why the fork step sometimes has to happen on GitHub — see Your repo vs theirs.

The tour · in order

From signing in to a pull request

These steps are a real sequence — each one depends on the one before it, which is why they're numbered.

  1. 01

    Connect GitHub

    The landing page has two buttons. Connect GitHub starts the sign-in; Analyze public repository goes to the same place, because even public analysis needs a GitHub identity to keep API limits workable.

    Connect GitHubAnalyze public repository

    GitHub asks you to authorize, then drops you on the dashboard. There is no signup form — your GitHub identity is the account. Sign out from the avatar menu, top right.

  2. 02

    Install the app on the accounts you'll work in

    If the top bar shows Install app, CodeWeave has no installation on your account yet. Install it and choose All repositories for the account whose code you want to change. Without this, private repos stay invisible and nothing can be written.

    Install app
  3. 03

    Dashboard — pick or paste a repository

    Four counters (repositories, indexed, AI changes, pull requests), a paste box, then a card per repository you've analysed. Repositories in the sidebar lists everything your GitHub account can reach, with filters for indexed / writable / private.

    owner/repoor https://github.com/owner/repo→Analyze

    Each card carries the two facts that decide everything: the access badge and the index state.

  4. 04

    Index it — this is the step that makes the AI useful

    Nothing intelligent works before this. Index repository reads the file list, throws away noise (dependencies, build output, images, lock files), parses the real source with a JavaScript AST parser, cuts it into chunks around functions and classes, turns each chunk into a vector, and records how files import and call each other.

    file list→filter→ parse→chunk→ vectors+relationship graph

    The counters that climb are real: files discovered, files processed, chunks, embeddings, symbols. Re-index re-runs it. A banner appears when new commits have landed since the last index — answers say so rather than pretending to be current.

The tour · the seven tabs

Inside a repository

Once a repository is open, everything lives in seven tabs. The first four only read; the last three can write.

  1. 05

    Overview — what is this project?

    Counters come straight from the index: files, lines, symbols, graph edges. Below them, the languages, the detected stack read out of package.json and friends, entry points, key directories, and the HTTP routes the parser actually found. The written summary is the only AI part — the numbers are facts.

    Regenerate
  2. 06

    Files — read the code, with the assistant beside it

    Explorer on the left (a dot marks an indexed file), read-only editor in the middle, assistant on the right. The panel toggle hides the assistant; the arrow opens the file on GitHub. Nothing here edits code.

  3. 07

    AI Assistant — answers that cite the code

    Ask in plain English: "How does creating a user work, from the route down to the database?" The answer is built only from retrieved chunks of this repository, and every claim carries a source like src/services/user.service.js:4-9. Click a source and the file opens at that line, highlighted.

    If retrieval finds nothing relevant it says so instead of inventing an answer — and tells you how much of the repository is actually indexed.

  4. 08

    Impact — what breaks if I change this?

    Search a function or class name, pick it, and CodeWeave walks the stored relationship graph: who calls it, which modules import it, which HTTP routes end up exposing it, and which tests touch it. Severity comes from that graph, not from the model's mood.

    HIGH · calls it directly MEDIUM · imports the module LOW · related code

    "No test file references this symbol" is stated plainly when it's true — that's often the useful part.

  5. 09

    Changes — describe it, read the diff, then decide

    Type what you want in plain English. CodeWeave retrieves the relevant files, asks for the smallest patch that does the job, then checks the patch against the current commit before showing it to you. It can edit existing files and create new ones. 

    @@ src/services/user.service.js
      async function addCredits(id, amount) {
    +   if (amount <= 0) throw new Error('Credit amount must be positive');
        const user = await getUserById(id);

    Reject discards it — nothing was ever on GitHub. Accept change opens a form where you can edit the branch name, commit message, PR title and description, and switch the pull request off if you only want the commit.

    RejectAccept change

    Every proposal is kept in Change history below, and in AI Changes in the sidebar.

  6. 10

    Architecture — the shape of the codebase

    A map of directories drawn from real import edges. Modules nothing imports sit on the left (entry points), modules that import nothing internal sit on the right (leaves), and a box outlined in the accent colour exposes HTTP routes. Below it, the strongest dependencies ranked by number of imports.

  7. 11

    Pull Requests — read them, and have them reviewed

    Open / closed / all, with a badge on any PR that already has an AI review. Open one to get the description, commits, per-file diffs, and Run AI review.

    The review reads the diff plus the current file contents, the dependants from the graph, and the test files. Findings are labelled by confidence — CONFIRMED LIKELY POSSIBLE — so you can tell a certainty from a guess. Publish to GitHub posts it as a comment. It never approves or rejects for you.

    Run AI reviewPublish to GitHub

The fork in the road

Your repository vs someone else's

Reading is identical either way. Only the moment you press Accept change differs.

Read & write

A repository you can push to

Accept→new branch→ commit→pull request

One click and it's done. The branch is created from the exact commit the AI reviewed, the files land in one commit, and the pull request targets your default branch — which is never written to directly.

example: Thermo041/VedaAI

Read only

A repository owned by someone else

Accept→your fork→ branch→commit→ PR upstream

Nothing is ever pushed to their repository. The commit goes to your fork; the pull request goes to them, exactly as if you had done it by hand.

example: hagopj13/node-express-boilerplate

The one manual click, and why it exists. GitHub only lets an app create a fork of a repository your own installation covers — which never includes a stranger's account. So for a third-party repo, CodeWeave shows Fork on GitHub (one click there), then I've forked it — check again. From that point it is automatic again: it finds your fork, branches from the reviewed upstream commit, commits, and opens the pull request. Nothing about this is a workaround for a missing feature — no GitHub App can do it any other way.

Consequences

Exactly four things can appear on GitHub

Everything CodeWeave writes is one of four ordinary GitHub objects, created as you, visible in the normal places, and undoable by hand. There is no hidden fifth thing.

ObjectWhen it appearsWhat it looks like
A branch You press Create branch, commit & open PR codeweave/reject-negative-credits-0bziwh — cut from the exact commit the AI read. If the name is taken it becomes -2, -3.
One commit Immediately after the branch All files in the change, in a single commit, with your message. No fixup commits, no force-push.
A pull request Unless you switch it off in the accept form Targets the default branch. Body is generated — see below — and fully editable before you submit.
A comment on a pull request You press Publish to GitHub, or a webhook review runs An ordinary issue comment holding the review findings. Not an approval and not a "request changes".

The pull request body it writes

  • Summary — what the change does.
  • Files changed — each path with +additions / -deletions.
  • Why — the model's reasoning, when it gave any.
  • Review notes — the model's own warnings, kept rather than hidden.
  • Callers to double-check — pulled from the relationship graph, not guessed.
  • Requested change — your original instruction, quoted verbatim.
  • A closing line naming CodeWeave, and saying if it came from a fork.

What it will not do, enforced on the server

  • Commit to the default branch — refused even if the branch field is edited to main.
  • Merge, approve, or request changes on any pull request.
  • Force-push, rewrite history, or delete a branch.
  • Touch a file that was not in the context the AI read.
  • Push anything to a repository you cannot write to — that goes to your fork instead.
  • Commit a patch whose base file moved since it was proposed.
The last check happens after the branch exists. Between generating a change and accepting it, someone else may have pushed. So the file is fetched again from the new branch and compared to what the AI actually read — by content hash, not by timestamp. On a mismatch you get "changed on GitHub after this change was proposed", the commit never happens, and you regenerate against current code.

Without you asking

Two things happen on their own

Once the app is installed on an account, GitHub tells CodeWeave when code lands and when pull requests open. Two jobs run off that, both queued in the background so GitHub is answered instantly and the work happens after.

on push

The index catches up, cheaply

push→changed files only→ re-parse→re-embed→graph

A push touching three files re-reads those three files, not the repository. Deleted files lose their chunks, symbols, and graph edges. Answers and impact analysis are current again without anyone pressing Re-index.

up to 120 changed files per push

on pull request

The review is waiting when you look

opened/reopened/ new commits→AI review→ comment on the PR

The same review you get from Run AI review, triggered by GitHub and posted as a comment. Pushing more commits to an open pull request re-runs it against the new head.

drafts wait until marked ready for review

Nothing happens whenWhy that is right
The repository was never analysed in CodeWeaveThere is no index to update and nobody asked for one.
It has never finished indexingAn incremental update needs something to be incremental against.
The push went to a branch other than the indexed oneYour feature branch shouldn't rewrite the index of main.
The push created or deleted a tag, or deleted a branchNo file contents changed.
The pull request is a draftIt isn't ready for readers, so it isn't ready for review.
The same delivery arrives twiceGitHub retries; the delivery ID is remembered, so the work runs once.
The delivery isn't signed by GitHubIt is rejected before the payload is even parsed.

All of it is on the record: Activity in the sidebar lists AI changes, AI pull request reviews, and indexing jobs, each with the outcome — including the ones that decided to do nothing, and why.

No installation, no automation. Analysis and answers work on any public repository with just a signed-in GitHub account. But nothing arrives by itself until the app is installed on the account that owns the repository — you'll simply see the "changed since it was last indexed" banner and re-index by hand.

When it says no

If something looks wrong, it is usually telling you the truth

Most refusals here are GitHub's answer about your account, or a guardrail that caught a patch it could not apply safely. Both are worth reading literally. These are the ones people actually hit.

Access

What you seeWhat it meansWhat to do
Install app in the top bar, or private repositories missing from the list CodeWeave has no installation on that account, so GitHub won't show it private repositories or let anything be written. Install it, choose the right account, and pick All repositories unless you have a reason not to.
Read only on a repository you own Either you're signed in as a different GitHub account, or the installation covers a different account. Installations are never shared between accounts. Check the login in the avatar menu, then Settings → App installations for the account that owns the repo.
"CodeWeave cannot fork this repository for you" Not a bug and not a missing feature: GitHub only lets an app fork repositories its own installation covers, which never includes a stranger's account. Fork on GitHub — one click — then I've forked it — check again. Everything after that is automatic.
"You don't have access to this private repository." Your GitHub account cannot see it, so neither can CodeWeave. Not even file names are returned. Get access on GitHub, or analyse a repository you can reach.
Reconnect GitHub, or "GitHub authorization failed" The short-lived GitHub token behind your session has aged out. Press it. You keep your repositories, indexes, and change history.

Changes and indexing

What you seeWhat it meansWhat to do
"This repository has changed since it was last indexed" New commits landed after the index was built. Answers are honest about being behind rather than quietly stale. Re-index repository — or install the app on that account and pushes sync themselves.
"…changed on GitHub after this change was proposed" Someone pushed between generating the change and accepting it, so the patch no longer matches the file. Nothing was committed. Generate the change again; it will be built against the current code.
"The AI tried to modify … which was not part of the reviewed context" A guardrail. The model reached for a file that was never retrieved, so its edit was refused rather than applied blind. Ask again, naming the file or function you mean, so it is retrieved as context.
"…is too large for a full-file rewrite" or "likely truncated" The model tried to reprint a big file and would have dropped part of it. Refused instead of committing a mutilated file. Ask for a narrower change — one function, one behaviour.
"Could not generate a safe change" Nothing usable survived validation for this instruction. Rephrase concretely: what should happen, where, and to what. Vague instructions fail this step most often.
The assistant says it cannot find anything relevant Retrieval came back empty — often a partial index, or a question about code that isn't in this repository. Check the indexed coverage it reports, re-index if it is low, and mention a real file or symbol name.
"Indexing failed" A GitHub read or an embedding call gave out partway through. Activity → Indexing jobs holds the actual error. Re-indexing after a transient failure usually just works.
A pull request opened, but no review appeared Automatic review needs an index and a non-draft pull request on a tracked repository. Index the repository, or open it and press Run AI review.

Limits, per account

12 change generations or reviews per 5 minutes. 15 other AI requests per minute.

Indexing

10 index runs per 10 minutes. Automatic syncs after a push don't count against it.

GitHub writes

20 per minute — far above anything a person does by hand, and there to catch loops.

One habit covers most of it. Read the message rather than retrying the button. Nearly every refusal in CodeWeave names the file, the account, or the permission it is talking about, because the alternative — a patch applied to code the model never saw — is the failure that actually costs you something.
